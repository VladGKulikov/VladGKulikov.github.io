A language model can propose a solution without learning anything from its outcome. We can keep a successful answer, discard a failed one, or ask for another attempt. None of those operations necessarily changes what the model will do next time. Learning requires a further connection: the result of an action must influence the rule that selects future actions.

Reinforcement learning, or **RL**, studies that connection. In this course, an action may be a step through a small environment, a token generated by an LLM, or an agent's call to a tool. Module 1 develops a common language for these cases. We begin with an interaction, distinguish it from a learning update, and then use that distinction to make sense of the method names used throughout the course.

No prior RL course is required. You should be comfortable with Python, basic PyTorch, probability, gradient optimization, and the Transformer architecture.

If you have studied classical RL, skim §§1.1.1–1.1.3 and spend more time on §§1.1.4–1.1.6, where familiar notation is connected to LLMs and the boundary between RL and neighboring post-training methods is made explicit.

## Lesson 1.1. The Minimum Language of Reinforcement Learning

We will follow a decision through its consequences before collecting the terminology. The definitions name parts of that process: who acts, what changes, what is observed, and what is learned. Once those roles are clear, ordinary text generation will already contain something we can recognize as a policy.

### Step 1.1.1 — What RL is: one loop before a catalog of algorithms

Suppose a language model writes a program and the tests report a failure. We have feedback, but not a replacement token for every mistaken decision. We could request another answer, choose a different candidate, or use the result to change how the model behaves on future requests. Only the last operation trains the model itself.

In **supervised learning**, an example usually comes with a target: an image class, a translation, or a spam label. In **self-supervised learning**, the target is extracted from the data; the next token is already present in the corpus. The testing example has a different order. The system first proposes a solution, then discovers what that choice achieved. A test can judge a completed program without demonstrating the full sequence of decisions needed to write a correct one.

RL calls the decision-making system an **agent**, the mechanism that receives its actions and produces their consequences an **environment**, and the numerical feedback a **reward**. Inside the agent, a **policy** $\pi_\theta$ determines how actions are chosen. The complete system may be complicated, but its behavior becomes much easier to read when we distinguish two loops.

![Two nested loops in online RL](assets/rl-for-llm/en/module-01/M1_rl_feedback_loop_EN.png)

**The first loop is interaction.** The agent receives a state or observation and selects an action $a_t$. The environment responds with the next observation $o_{t+1}$ and a local reward $r_{t+1}$. The next decision is made in the situation that has now been reached. A sequence of these transitions forms a rollout, or trajectory $\tau\sim p_\theta$.

In a small corridor, an action is a move left or right, and reaching the right terminal state yields $+1$. In token generation, the selected token is appended to the text and becomes part of the context for the next choice. When a verifier scores only the finished response, a whole generation separates the first decision from meaningful feedback.

**The second loop is learning.** Collected trajectories receive scores: accumulated environment rewards, executable test results, or reward-model evaluations. A learning algorithm uses this experience to update $\theta\rightarrow\theta'$. The behavior rule has now changed, and so has the distribution it can induce over future trajectories: $p_{\theta'}(\tau)$ need not equal $p_\theta(\tau)$.

The figure keeps those time scales apart. A system can produce an entire answer with fixed weights. Receiving an observation or reward is not itself a parameter update; a separate learning step must connect the feedback to a change in behavior. We are not choosing that algorithm yet. We are identifying what it has to connect.

This is the feedback structure of online RL: the policy affects the experience collected, the experience informs an update, and the new policy produces the next experience. **Agent and policy are therefore not synonyms.** The policy selects actions within the system, the environment determines their consequences, and the learning algorithm changes the selection rule.

> **RL studies how to choose actions from feedback so that the expected outcome of a sequence of decisions improves.**

We will make “expected outcome” precise and later consider a setting in which the experience has already been collected. Throughout, the useful distinction remains the same: taking an action, observing its consequence, and changing future behavior are different operations.

### Step 1.1.2 — Agent, environment, state, action, and reward

Consider one move in the corridor. Before acting, the agent receives information about its situation. After the move, its position changes, and arriving at a terminal may produce a reward. The situation itself, the information available about it, and the selected move are three different objects. The small environment makes them easy to see; a language system needs the same distinctions.

We can now give the components stable names. At time $t$:

- the **agent** is the decision-making system;
- the **environment** is everything that responds to the agent's actions and determines their consequences;
- the **state** $s_t$ describes the situation well enough to model the next transition;
- the **observation** $o_t$ is the information actually available to the agent and may be incomplete;
- the **action** $a_t$ is the agent's choice from an action space $\mathcal{A}$;
- the **reward** $r_{t+1}\in\mathbb{R}$ is a local scalar signal following an action;
- the **transition** $P(s_{t+1}\mid s_t,a_t)$ describes environment dynamics;
- an **episode** runs from an initial condition to a terminal condition or time limit;
- a **trajectory** $\tau=(s_0,a_0,r_1,s_1,a_1,r_2,\ldots)$ records an episode.

When the chosen state contains all information needed to determine the distribution of the next state and reward, the model is a **Markov decision process** (MDP). “Markov” does not mean that the world has no memory; it means that all relevant memory has been included in the state.

A finite MDP is often written as

$$
\mathcal{M}=(\mathcal{S},\mathcal{A},P,R,\rho_0,\gamma),
$$

where $\mathcal{S}$ is the state space, $\mathcal{A}$ the action space, $P$ the dynamics, $R$ the reward rule, $\rho_0$ the initial-state distribution, and $\gamma$ the discount factor. Most of these objects already appeared in one transition. The initial distribution tells us where interaction begins; discounting will matter when we combine rewards across time. The tuple collects the task specification rather than replacing its explanation.

The same concepts can be placed side by side in a toy environment and in an LLM.

| Concept | Corridor | Token generation by an LLM |
|---|---|---|
| Agent | a system choosing movements according to its policy | a generation system whose policy is parameterized by a Transformer |
| Environment | cells and terminal states | token append, length limit, evaluator |
| State | cell index | prompt + generated prefix |
| Action | left / right | next token |
| Reward | $+1$ at the right terminal | for example, whether tests pass or how the response is scored |
| Episode | path to a terminal | generation until an end-of-sequence token or a length limit |

In the task considered here, an **end-of-sequence** token (EOS) marks completion, much as a terminal cell ends the corridor path. An external length limit has a different cause: collection stops even though the process might have continued. For now, we only need to keep the causes distinct. Module 2 will show why the distinction matters when estimating future return.

Do not confuse a **reward** with the **environment**. A learned reward model, a unit-test suite, a mathematical verifier, or a user may compute the reward. The environment also includes transitions, constraints, hidden tool state, and everything else that determines the next step.

### Step 1.1.3 — Policy: a rule for choosing actions

A **policy** is the rule by which an agent chooses an action.

A deterministic policy returns one action:

$$
a=\mu(s).
$$

A stochastic policy defines a probability distribution over actions:

$$
\pi(a\mid s)\ge0,
\qquad
\sum_{a\in\mathcal{A}}\pi(a\mid s)=1.
$$

In deep RL, the policy is usually parameterized by a neural network:

$$
\pi_\theta(a\mid s),
$$

where $\theta$ denotes trainable weights. The network first produces action scores, those scores are converted into a distribution, and a concrete action is then selected from that distribution.

The policy is the entire distribution $\pi_\theta(\cdot\mid s)$, not the action already selected. A particular run produces one sample $a_t$; another run in the same situation may choose differently. Reward belongs to the other side of the interaction: it evaluates a consequence and is not a probability assigned by the policy.

For an LLM, this separates likelihood from usefulness. A high token probability says that the model is inclined to produce that token. It does not say that the completed program will pass its tests. Reward-based learning is meant to connect those inclinations to the consequences the task cares about.

Stochasticity is not present merely for “randomness.” It permits exploration, produces diverse experience, and allows relative action probabilities to change smoothly. At inference time a policy may be made nearly deterministic, but collapsing it too early during training can remove useful alternatives.

### Step 1.1.4 — An LLM as a policy: the exact correspondence and its boundary

We can now build the main bridge of the course.

Let $x$ be a prompt and $y_{<t}=(y_1,\ldots,y_{t-1})$ the generated prefix. In a token-level formulation,

$$
s_t=(x,y_{<t}),
\qquad
a_t=y_t.
$$

The Transformer produces logits $z_\theta(s_t)$. Begin with the base sampling rule: an ordinary softmax, with no further decoding transformations. The next-token distribution is then

$$
\pi_\theta(a_t\mid s_t)
=
\operatorname{softmax}\!\left(z_\theta(s_t)\right)_{a_t}.
$$

Thus an **LLM really is $\pi_\theta(a\mid s)$**: the context is the state, the next token is the action, and the Transformer weights are the policy parameters. Within this token-level abstraction, the correspondence is mathematical rather than metaphorical.

![An LLM as a token policy](assets/rl-for-llm/en/module-01/M1_llm_policy_EN.png)

Producing one particular response requires selecting each of its tokens in turn. Each probability is conditioned on the choices already made; these are not independent predictions. The probability of the complete response therefore factorizes autoregressively:

$$
\pi_\theta(y\mid x)
=
\prod_{t=1}^{T}
\pi_\theta(y_t\mid x,y_{<t}),
$$

and the log-probability converts the product into a sum:

$$
\log\pi_\theta(y\mid x)
=
\sum_{t=1}^{T}
\log\pi_\theta(y_t\mid x,y_{<t}).
$$

These two equations will reappear in policy-gradient methods and in regularization by the **Kullback–Leibler divergence** (KL). We will name the concrete preference and group-relative algorithms after the basic formulation is complete.

Two boundaries matter.

- Calling an LLM a policy describes **how it chooses actions**; it does not claim that its weights were necessarily trained with RL. A pretrained model already defines a policy even though it was trained by next-token prediction.
- In a deployed system, the LLM is usually **a policy or a policy component**, not the whole environment. External tools, files, browsers, users, and verifiers have their own state and dynamics.

“An LLM is a policy” is therefore exact once the state and action have been specified. Temperature and other logit transformations change the distribution actually used for selection. We will see temperature in Lesson 1.4 and the full behavior-policy contract in Module 6. The correspondence still holds; we must simply identify the distribution from which the action was really drawn.

### Step 1.1.5 — Reward, return, discounting, and the RL objective

A reward $r_{t+1}$ belongs to one transition. The **return** is the accumulated future reward from time $t$:

$$
G_t
=
\sum_{k=0}^{T-t-1}\gamma^k r_{t+k+1},
\qquad
G_t=r_{t+1}+\gamma G_{t+1}.
$$

Here $\gamma\in[0,1]$ is the **discount factor**. It may serve several roles:

1. assign lower weight to more distant consequences;
2. control an effective planning horizon;
3. make an infinite-horizon sum converge.

Finite-response LLM training often uses $\gamma=1$: EOS or a maximum length already bounds the episode, and the final score applies to the response as a whole. This is not universal. Delay, time cost, and interruption risk can make $\gamma<1$ meaningful in long agentic tasks.

For rewards $[1,0,0,10]$ and $\gamma=0.9$,

$$
G_0
=
1+0.9\cdot0+0.9^2\cdot0+0.9^3\cdot10
=
8.29.
$$

The value 8.29 describes an episode that has already happened. A policy, however, is not useful merely because it once produced a good outcome. Repeating it can lead to other actions, initial conditions, and consequences. We therefore move from the result of one trajectory to the expected result of the rule that generates trajectories.

The RL objective fits in one line:

$$
\max_\theta J(\theta)
=
\mathbb{E}_{\tau\sim p_\theta}
\left[G_0(\tau)\right].
$$

Read it in words: we seek policy parameters under which **trajectories produced by that policy in the selected environment have high average return**.

The expectation includes the randomness specified by the task: the starting situation, the policy's choices, and the environment's responses when those are stochastic. Even for one fixed prompt, an LLM may produce different solutions. One successful answer does not tell us how often the model will succeed; that requires information about the distribution of outcomes.

The feedback loop now closes. Parameters $\theta$ determine the policy, the policy influences the trajectories collected, and experience is used to estimate the objective and construct an update. Module 4 will explain how to obtain such an update without differentiating the testing program. Here, the important point is what the update is intended to improve.

#### Mathematical deepening: where the policy parameters enter the trajectory distribution

> You can skip this section on a first reading. Module 4 derives the policy gradient and uses this factorization in full.

For a finite, fully observed MDP,

$$
p_\theta(\tau)
=
\rho_0(s_0)
\prod_{t=0}^{T-1}
\pi_\theta(a_t\mid s_t)
P(s_{t+1}\mid s_t,a_t)
P_R(r_{t+1}\mid s_t,a_t,s_{t+1}).
$$

Here $P_R$ is the reward distribution; for a deterministic reward it is concentrated on one value. In this factorization, the initial distribution, dynamics $P$, and reward rule $P_R$ are fixed with respect to the policy parameters $\theta$; dependence on those parameters enters through $\pi_\theta$. This is an assumption about the task parameterization, not the definition of model-free learning. Whether the algorithm uses a model of the environment is a separate question, introduced in Lesson 1.3. After an update, action frequencies change, and so do visited states, errors, and rewards. A new LLM checkpoint generates a new response distribution and, in an agentic task, may reach different external states.

### Step 1.1.6 — Why RL is not merely “learning without a correct answer”

Return to the program evaluated by tests. The task may have a perfectly definite correct result. Yet checking a finished program need not tell the learner which construct should have been chosen halfway through generation. **A criterion for correctness is not the same thing as a demonstration of correct decisions.** This is why “RL has no correct answer” is not a reliable boundary.

In **imitation learning**, an expert provides actions or complete solutions. They can be learned through supervision even when the task itself is sequential. **Behavior cloning** uses trajectories, but its objective is the likelihood of expert actions in the recorded data rather than direct maximization of the current policy's expected return.

In **offline RL**, no new interaction is available during optimization. The learner has a fixed collection of trajectories and consequences, yet the goal of improving decisions according to reward remains. The collection loop is closed for the duration of learning. A fixed log, or the absence of fresh interaction, does not by itself turn an RL problem into demonstration copying.

A **contextual bandit** provides a shorter formulation. One action is selected for a context, it receives feedback, and no further decision within that round is modeled. Preference learning provides an explicit comparison—response A was preferred to response B—but the chosen loss determines how that observation changes the model. Pairwise supervision does not name a single universal RL algorithm.

Rather than settling the label before specifying the problem, this course will ask four questions.

1. **What decision does the policy make?** A token, a complete response, or a tool call?
2. **What feedback is available?** A demonstration, a preference, a learned reward, or a verifiable outcome?
3. **Are there sequential consequences and a credit-assignment problem?**
4. **Who generated the data?** A fixed dataset, the current policy, an older policy, or inference-time search?

These questions are a way to read a system, not another taxonomy to memorize. In **online RL**, the policy helps determine the next experience collected. Offline RL removes that opportunity during training. In both settings, we still need to know which consequences should improve and what evidence supports the improvement.

> **A policy chooses actions; the environment determines consequences and rewards; RL searches for a policy with high expected return. The concrete algorithm is determined by how data is collected and how that expectation is estimated.**

## Lesson 1.2. Choosing an RL Formulation for an LLM

The same generation can be described at several resolutions. Sometimes we care only about a complete response and its score. Sometimes we need every token probability. Tool use introduces changes outside the text as well. We will separate the choice of action scale from two further questions: what the agent observes and how time passes between decisions.

### Step 1.2.1 — Three useful abstractions: response, token, and macro-action

For the programming example, we could initially look only at the finished answer and its test result. We could then open up that answer into token-by-token decisions. Or we could let the model use tools and revise the program in response to their output. Each system contains an LLM, but the boundaries of a decision and a trajectory differ.

“An LLM is an MDP” is therefore incomplete. First choose the **unit of action**, then specify the available information and transition rule. The table collects three useful formulations; it is not a ladder from simple models to superior ones.

![Three abstractions for an LLM task](assets/rl-for-llm/en/module-01/M1_llm_abstractions_EN.png)

| Formulation | Context or state | Action | Transition | Useful for | What it deliberately hides |
|---|---|---|---|---|---|
| **Contextual bandit** | prompt $x$ | complete response $y$ | no next decision is modeled | single-turn preference learning with a terminal reward | token-level credit assignment and decoding cost |
| **Finite token-level MDP** | full prefix $(x,y_{<t})$ | next token $y_t$ | deterministic token append | log-probabilities, KL, policy gradients, response length | hidden external state and coarse actions |
| **Partially observable Markov decision process** (POMDP) or **semi-Markov decision process** (semi-MDP) | observations, history, memory | message, tool call, or macro-action | an external, possibly hidden environment changes | browsers, coding, games, long dialogue | explicit treatment of time, tool failures, and partial observability |

#### What each name actually claims

Once the action scale is chosen, two further questions remain: what does the agent know about the situation, and how much time passes between decisions? This is where MDPs, POMDPs, and semi-MDPs differ. A response versus a token is a choice of scale; observability and duration are properties of the resulting formulation.

In an **MDP**, the chosen state contains everything relevant to the distribution of the next transition and reward. Once that state is fixed, earlier history should add no predictive information. For pure autoregression under fixed rules, the full prefix $(x,y_{<t})$ supplies such a state: the selected token is simply appended to it. Step 1.1.2 gives the formal definition.

A **POMDP** keeps a Markov model for the hidden environment state but does not expose that state in full to the agent. An **observation** may be incomplete or noisy: a file has not been read, a remote service has an unknown status, or a user's intent remains unclear. Decisions must rely on the available history and memory. This does not mean that the past is unusable. It means that the currently visible input need not reveal the state of the outside world.

A **semi-MDP** addresses duration. A Markov model is defined at decision epochs, but the actions between those epochs may take different amounts of time. A one-second call and a one-minute call each occupy one entry in the action log while consuming different time budgets. Their duration may therefore matter to cost and to the valuation of later consequences.

Partial observability and variable duration can coexist. Accounting for time does not reveal hidden information, and giving an agent more memory does not make its tools equally fast. Module 11 will develop these features for agentic RL. Here, it is enough to know which part of the problem each name describes.

#### A complete response as one action

Let $x$ be a prompt, $y$ a complete response, and $r(x,y)$ a reward. Then

$$
J(\theta)
=
\mathbb{E}_{x\sim\mathcal{D},\,y\sim\pi_\theta(\cdot\mid x)}
[r(x,y)].
$$

This is a contextual-bandit representation. It is convenient for deriving a response-level objective: one context produces one macro-action and one reward. It does not claim that the response physically appears in one step; internal decoding has been deliberately collapsed.

#### One token as an action

Let

$$
s_t=(x,y_{<t}),
\qquad
a_t=y_t,
\qquad
s_{t+1}=s_t\mathbin{\Vert}a_t.
$$

Until EOS, the transition is deterministic: the selected token is appended to the prefix. This model is natural for log-probabilities, KL, policy gradients, and response length. If the complete prefix contains all information relevant to the selected task, the formulation is Markov.

#### A message or tool call as an action

After a browser, shell, or test-runner call, the external world changes: a file has been overwritten, a server returned an error, or a user clarified the goal. The message window available to the agent need not reveal the full external state, so a POMDP can be a useful formulation. If actions have different durations—for example, one tool call takes a second and another contains a minute of internal work—a semi-MDP may be more natural than a token model.

**Course rule:** before an important equation, we will state what counts as the state, action, and reward. The same LLM can be a policy in all three formulations, but the meaning of a trajectory and the difficulty of credit assignment change.

### Step 1.2.2 — Sparse reward, credit assignment, and rollout cost

A **rollout** is one trajectory generated by the policy: a complete response or a sequence of agent actions in an environment.

Many LLM tasks reveal the reward only at the end of the rollout:

- did the unit tests pass;
- did the final numerical answer match;
- did the agent complete the browser task;
- did an evaluator prefer one response over another.

Such feedback is a **sparse reward**, often a **terminal reward**. If a response contains one thousand tokens and receives only a final $0$ or $1$, the credit-assignment problem is immediate: which decisions caused success or failure?

One final score compresses many decisions. A mistake may have been introduced early and become visible only in the final line; a successful response may contain essential steps alongside unnecessary ones. Two related tasks follow: reduce the random variation in the learning signal, and obtain more local information about the consequences of decisions.

A **value function** and a **critic** estimate the expected future outcome from the current situation. They provide a reference against which an observed return can be better or worse than expected. Comparing several responses to the same prompt produces a **group baseline**, keeping the comparison within a common context. That comparison can help organize the signal without identifying the particular token responsible for success.

**Process rewards** provide feedback before the end when an intermediate property can be assessed reliably. Task decomposition and deliberate reward design can attach feedback to larger actions. These mechanisms do different jobs: a more useful reference, a less noisy estimate, and an additional observation about the solution process are not the same improvement.

#### A preview of policy gradients

> You can skip this section on a first reading. Module 4 gives the full derivation.

In many policy-gradient methods, the contribution of a selected action has the form

$$
A_t\,\nabla_\theta\log\pi_\theta(a_t\mid s_t),
$$

where $A_t$ is the **advantage**: how much better or worse the selected action was than an expected baseline. In the simplest REINFORCE form, one final return affects the log-probabilities of all actions in the trajectory. The estimator may be unbiased while still having high variance.

None of these methods turns a poor reward into the right objective. Denser or less noisy feedback only helps optimize what was actually specified.

There is also a systems cost. In an abstract token-level MDP, “append a token” is nearly free, but selecting that token requires a forward pass through a large model. For long responses, rollout generation is often the dominant cost. Agentic RL adds tool latency, sandboxing, networking, and retries. Statistical sample efficiency and inference-system throughput therefore meet in one engineering problem.

## Lesson 1.3. A Modern Map of LLM Post-Training

The vocabulary now gives us a way to compare methods without treating their names as definitions. First we will distinguish operations performed on models and responses. Then we will ask which classical RL questions still apply and what language systems add. The tables are a map for later reading, not a requirement to master every algorithm before continuing.

### Step 1.3.1 — Where RL sits in the LLM lifecycle

Think of several operations, not one mandatory queue of training stages. A model can learn continuations from a corpus. It can learn to reproduce demonstrations. It can be trained on comparisons between completed answers. It can generate fresh responses, receive feedback, and update its policy. Or the system can leave the weights alone and select one answer from several attempts.

The first distinction is **what information is supplied and what changes afterward**. **Supervised fine-tuning (SFT)** supplies demonstrations of desired behavior. **Direct preference optimization (DPO)** uses preferred/dispreferred pairs. **Reinforcement learning from human feedback (RLHF)** connects human feedback to policy improvement; one familiar pipeline first trains a reward model from comparisons.

**Proximal policy optimization (PPO)** and **group relative policy optimization (GRPO)** name update mechanisms. **Reinforcement learning with verifiable rewards (RLVR)** answers a different question: where does the score come from? It is supplied by an executable or otherwise explicitly specified checking procedure. **Kullback–Leibler divergence (KL)** measures distributional difference and is often used to make departure from a reference policy costly.

There is no need to derive the algorithms yet. Start with the last two columns of the table: must new responses be collected, and are parameters updated? Then read the data and objective that belong to each operation.

| Operation | Data and feedback | Optimized quantity | Fresh generations from the current policy required? | Parameters updated? |
|---|---|---|---|---|
| **Pretraining** | text sequences; the next token is observed | log-likelihood / cross-entropy | no; the corpus is fixed | yes |
| **SFT / behavior cloning** | demonstrations of desired responses or actions | demonstration likelihood | no | yes |
| **DPO as an example of direct preference optimization** | fixed preferred/dispreferred pairs | a pairwise preference loss relative to a reference policy | not during the update itself | yes |
| **PPO-RLHF or GRPO/RLVR** | responses or trajectories from the current or recent policy plus a reward or verifier | expected reward, often with KL regularization | yes | yes |
| **Best-of-N** | $N$ candidates plus a scorer or verifier | candidate selection with a fixed model | generations are needed for the request | no |

**Post-training is not one particular RL loop.** Demonstrations and fixed preferences can both matter to a system while supporting different objectives. Fixed data alone do not mark the boundary of RL; offline RL has already shown why. Best-of-N differs even earlier: it chooses an answer with frozen weights, so selection does not automatically become behavior learned by the model.

The same program checker could therefore serve two purposes. At inference time it helps choose an answer for this request. During training, its result contributes to changing the distribution of future answers. The source of feedback may be identical while the operation performed on the model is different.

This table is an initial map of operations. The following sections add the coordinates needed to read an algorithm: who produced the data, which components learn, and what assumptions connect feedback to an update. A method name is not a complete experiment description.

> **Further reading:** Transformer architecture, pretraining, and SFT are covered in *Modern LLMs*. They are introduced here only to the depth needed for a self-contained RL route.

### Step 1.3.2 — What changed after classical RL: historical anchors

Language models did not remove the old RL questions. How can a decision be evaluated before the trajectory ends? How should a learner explore an alternative about which little is known? What can it infer from experience produced by a different behavior rule? Bellman equations, value functions, and policy gradients were developed to address questions of this kind, and those questions remain relevant.

The concrete objects changed. An action can now be a token or a tool call. Feedback may come from comparisons or an executable verifier. Collecting one episode can require expensive autoregressive inference. The history below is therefore not a replacement of obsolete RL by a new technology; it follows familiar mechanisms as their setting and implementation change.

| Year | Anchor work or line | What carries into this course |
|---|---|---|
| 2015 | **deep Q-network** (DQN) on Atari | deep value learning and replay as a classical off-policy line |
| 2016–2018 | AlphaGo / AlphaZero | self-play, policy/value learning, and **Monte Carlo tree search** (MCTS) as distinct system components |
| 2017 | PPO | near/on-policy rollouts and several epochs over a clipped surrogate objective |
| 2022 | InstructGPT | a practical SFT → reward model → PPO-RLHF pipeline |
| 2023 | DPO | a direct pairwise objective from a KL-regularized preference/RLHF formulation |
| 2024 | DeepSeekMath | GRPO: PPO-like optimization with a group baseline and no separately trained critic |
| 2025 | **Decoupled Clip and Dynamic sAmpling Policy Optimization** (DAPO), **GRPO Done Right** (Dr. GRPO), and **Group Sequence Policy Optimization** (GSPO) | different changes to clipping, normalization, group selection, and the level of the importance ratio |
| 2025–2026 | open agentic and model reports | increasing emphasis on interactive environments, tools, and long trajectories |

The primary sources and the precise status of each claim are listed in `Module_1_Sources.md`.

> **Frontier snapshot — 2026-07-14.** Public reports do not reveal one universal post-training stack. They describe several coexisting families: training on fixed preference data; PPO/GRPO-like optimization on fresh rollouts; RLVR for mathematics and code; and interactive RL for tool use and agentic tasks. Qwen3 reports a unified thinking/non-thinking design; Kimi K2/K2.5 reports joint RL stages including real and synthetic environments; GLM-5 reports asynchronous RL infrastructure and training on long trajectories in agent tasks. These are **claims made by primary technical reports**, not independent confirmation of a full recipe and not evidence that “the whole industry trains the same way.”

Read these anchors through the questions they address rather than as a sequence of winners. DQN illustrates value estimation, PPO updates from recent experience, InstructGPT gives a language-system role to a learned reward, and DPO and group-relative methods modify different parts of the learning construction. Their derivations come later. For now, the history explains why classical RL, data provenance, and infrastructure belong in the same course.

### Step 1.3.3 — Classical axes and their limits

Knowing that a system contains a neural network and receives reward is not enough to explain how it works. We need to ask whether it predicts action consequences, what it learns, and whose experience supplies the update. The classical coordinates ask different questions of one system; they are not mutually exclusive boxes in a single classification.

| Axis | Question | Examples |
|---|---|---|
| **model-free / model-based** | is a dynamics model used to plan consequences? | PPO is model-free; MCTS with a transition model is model-based planning |
| **value-based / policy-based / actor–critic** | which object is learned to choose actions? | DQN; REINFORCE; PPO |
| **on-policy / off-policy** | how closely do the data match the policy being updated? | REINFORCE and PPO are near/on-policy; DQN is off-policy |
| **online / offline** | are new interactions collected during training? | online RL; offline RL from fixed trajectories |

Start with the learned object. **Value-based** methods estimate the future outcome of a state or action, for example $Q(s,a)$, and use that estimate to select actions. **Policy-based** methods change the rule $\pi_\theta$ directly. An **actor–critic** learns both: the actor selects actions, while the critic estimates expected consequences and helps construct a lower-variance learning signal. Modules 2 and 4 will develop these estimates.

Next consider experience. **Online** learning allows new interactions during training; **offline** learning starts from a fixed collection. **On-policy versus off-policy** asks something else: does the policy being evaluated or improved match the behavior that generated the data? A replenished replay buffer, for example, can contain experience from several versions of an agent. Interaction continues, but many records no longer describe its present behavior. Offline and off-policy are related, not interchangeable.

Even “data from the current policy” does not imply one use per example. PPO collects a batch with $\pi_{\text{old}}$ and then performs several minibatch epochs while updating $\pi_\theta$. After the first change, the recorded distribution is no longer literally the distribution of the new weights. Step 1.3.5 will clarify how to read the update restriction; Module 4 will explain its mechanism.

Finally, the **model** in model-based RL is a model of environmental consequences used for planning. A large language model is not model-based merely because it is large or called a model. It may select commands without forecasting the external dynamics. The classification concerns what the system does with a transition model, not the label attached to its neural network.

### Step 1.3.4 — Five additional coordinates for LLM systems

The classical map describes learning mechanisms, but a language system may combine several stages, some of which perform no learning at all. A single quality score can also originate from tests, a human comparison, or another LLM. To reconstruct the process, extend the questions from the first lesson to the boundaries between its components.

1. **Feedback source:** demonstration, preference pair, learned reward, LLM judge, rule-based verifier, or environment outcome?
2. **Data source:** fixed dataset, fresh rollouts from the current policy, rollouts from an older policy, replay buffer, or inference-only candidates?
3. **Decision unit:** token, sequence, tool call, or long trajectory?
4. **What is updated:** policy, critic/value, reward model, reference policy, several components, or nothing?
5. **Where does optimization occur:** in parameters during training or in search and selection during inference?

![A map of post-training methods](assets/rl-for-llm/en/module-01/M1_method_map_EN.png)

Each question separates operations that can look similar from a distance. The same evaluator can filter training examples or supply an RL reward, but those uses change different parts of the system. A whole response can be the unit of reward while its probability is computed token by token. Training a reward model does not mean that the language policy has already been updated.

The map is consequently not a ladder from “worse” to “better.” SFT, DPO, PPO, GRPO, and Best-of-N can coexist and perform different jobs. When a new method name appears, reconstructing those jobs is more useful than trying to place it in a ranking.

### Step 1.3.5 — SFT, DPO, PPO-RLHF, GRPO/RLVR, and Best-of-N

We can now assemble a reference comparison. Step 1.3.1 separated operations on models and responses. This table applies the same questions to particular methods, emphasizing additional learned components and the precise meaning of an update.

| Method | Data | Feedback and objective | Fresh training rollouts | Additional trainable models | Precise characterization |
|---|---|---|---|---|---|
| **SFT** | fixed demonstrations | token-level maximum likelihood | no | none | supervised behavior cloning, not RL |
| **DPO** | fixed preference pairs | a direct pairwise loss relative to a reference policy | no | no separate reward model or critic | offline preference optimization derived from a KL-regularized RLHF formulation; not classical offline RL |
| **PPO-RLHF** | policy rollouts | learned reward + KL or constraints + PPO surrogate | yes | usually a reward model and critic/value | a near/on-policy actor–critic pipeline |
| **GRPO family in RLVR** | groups of candidates for one prompt | verifiable or scalar reward + group-relative advantage + PPO-like surrogate | usually yes | canonical GRPO has no learned critic | RLVR describes the feedback regime; GRPO is an algorithm; no critic does not mean no baseline |
| **Best-of-N** | $N$ inference-time candidates | a scorer or verifier selects the best | not a training question | none | inference-time search or selection with frozen parameters |

#### Why DPO should not simply be called offline RL

Offline first tells us that the data have already been collected. It does not specify their contents or the loss. Classical offline RL studies policy improvement from fixed records of interaction and reward, particularly when a new policy may select actions poorly represented in the log. Many familiar methods use value estimates and Bellman backups, but those operations are not the definition of the entire field.

DPO, in the setting considered here, receives pairs of compared responses and directly optimizes a pairwise policy objective. Its connection to RLHF comes from the derivation, not simply from the presence of a static file. We will therefore use the more informative description **direct offline preference optimization derived from a KL-regularized RLHF formulation**. Module 8 supplies the details. At this stage, the point is not to treat all fixed-data methods as one algorithm.

#### What on-policy means for PPO and GRPO

Rollouts are usually generated by a snapshot of the current or recent policy $\pi_{\text{old}}$, while $\pi_\theta$ is updated. The clipped surrogate removes an incentive for certain further ratio changes; it does not guarantee that actual ratios or KL remain within a fixed bound. Multiple epochs and asynchronous rollout systems create some stale or off-policy component; acceptable lag is part of the algorithm specification.

#### Why there is no single linear branch “after GRPO”

Several later methods revisit different GRPO components. DAPO changes clipping and dynamically removes uninformative groups; Dr. GRPO removes disputed normalizations; GSPO moves the importance ratio and clipping to the sequence level. They answer different questions about constructing an update, not one question about which method is newest.

A first reading need not unpack every modification. Keep the organizing idea: two algorithms can use the same responses and rewards while assigning different weights to their contribution. Module 9 will derive and compare those choices once the required machinery is in place.

### Step 1.4.2 — Temperature softmax: a first computable policy

Suppose the model produces $K$ logits $z=(z_1,\ldots,z_K)$. A logit is an unnormalized action score. The temperature policy is

$$
\pi_i(T)
=
\frac{\exp(z_i/T)}{\sum_j\exp(z_j/T)},
\qquad T>0.
$$

Exponentiation turns score differences into ratios of positive weights, and the denominator normalizes those weights to sum to one. Direct exponentiation can overflow for large logits. Subtracting the same maximum from each score introduces a common factor that cancels between numerator and denominator, leaving the distribution unchanged.

A numerically stable form subtracts the largest logit:

$$
\pi_i(T)
=
\frac{\exp((z_i-\max_jz_j)/T)}
{\sum_k\exp((z_k-\max_jz_j)/T)}.
$$

Small $T$ concentrates probability on high-logit actions. Large $T$ makes the distribution more uniform. This is one of the simplest ways to see a policy as a complete distribution rather than as “the selected token.”

How concentrated is the distribution over actions? **Entropy** measures this uncertainty by averaging $-\ln\pi_i(T)$ under the action probabilities themselves. An almost predetermined choice has little uncertainty; a uniform choice among several alternatives has more. This describes the spread of selection, not the quality of its outcome. A highly random policy can have high entropy and still fail often.

The policy entropy in nats is

$$
H(T)
=-\sum_i\pi_i(T)\ln\pi_i(T),
\qquad 0\le H(T)\le\ln K.
$$

A nat is the unit associated with the natural logarithm. The upper bound $\ln K$ is reached by the uniform distribution. The lower bound describes a certain choice; with finite logits and a positive temperature, ordinary softmax approaches that limit when there is a unique maximum.

Write the normalizing sum as $Z(T)=\sum_j\exp(z_j/T)$. Then $\log\pi_i(T)=z_i/T-\log Z(T)$. Substituting this expression into the entropy definition gives the first equality below. Differentiation must also account for the changing probabilities in the expectation. For **fixed finite logits with no top-k, top-p, or other transformations**, the result is

$$
H(T)=\log Z(T)-\frac{\mathbb{E}_{\pi_T}[z]}{T},
\qquad
\frac{dH}{dT}
=
\frac{\operatorname{Var}_{\pi_T}(z)}{T^3}
\ge0.
$$

The numerator of the derivative is the variance of the logits under the current distribution. It is non-negative, and $T^3>0$, so entropy cannot decrease as temperature rises. When all logits are equal, the distribution is already uniform and temperature changes nothing. This is an exact property of the specified function, not a promise that higher temperature improves answers.

![Entropy of a temperature policy](assets/rl-for-llm/en/module-01/M1_temperature_entropy_EN.png)

**Boundary of the statement.** A real API may combine `temperature` with top-p, top-k, repetition penalties, safety filters, and provider-specific transformations. The equation describes pure temperature softmax applied to a given set of logits, not the entire decoding pipeline.

> **Further reading:** *Information Theory for ML*, Module 2 covers entropy; Module 8 derives softmax as a maximum-entropy or Gibbs solution.

### Step 1.4.3 — Reproducible experiment: $T\mapsto H(T)$

For logits $z=(2,1,0,-1)$:

| $T$ | $H(\pi_T)$, nats | $H/\ln4$ |
|---:|---:|---:|
| 0.25 | 0.093113 | 0.0672 |
| 0.50 | 0.455429 | 0.3285 |
| 1.00 | 0.947537 | 0.6835 |
| 2.00 | 1.245050 | 0.8981 |
| 4.00 | 1.348243 | 0.9726 |
| 10.00 | 1.380071 | 0.9955 |

Read the two ends of the table. At temperature 0.25, almost all selection is concentrated on the highest-logit action, so entropy is small. At temperature 10, the distribution is close to uniform: 1.380071 is near the maximum for four actions. The final column expresses the same behavior as a fraction of that maximum.

Every row uses **the same logits**. No model was trained and no weights were updated; only the transformation from scores to selection probabilities changed. This simple distinction will later separate changes introduced by decoding from changes learned through optimization.

Minimal code:

```python
from __future__ import annotations

import numpy as np

def softmax_with_temperature(logits: np.ndarray, temperature: float) -> np.ndarray:
    logits = np.asarray(logits, dtype=np.float64)
    if logits.ndim != 1 or logits.size == 0:
        raise ValueError("logits must be a non-empty 1D array")
    if not np.isfinite(logits).all():
        raise ValueError("logits must be finite")
    if not np.isfinite(temperature) or temperature <= 0:
        raise ValueError("temperature must be finite and positive")

    scaled = logits / temperature
    scaled -= scaled.max()
    weights = np.exp(scaled)
    return weights / weights.sum()

def policy_entropy(logits: np.ndarray, temperature: float) -> float:
    p = softmax_with_temperature(logits, temperature)
    positive = p > 0
    return float(-(p[positive] * np.log(p[positive])).sum())
```

In the practice material, these functions become small checked exercises with worked explanations. They test not only the formula but numerical hygiene: $T\le0$, an empty vector, and `nan` must raise clear errors, while logits around 1000 must still produce finite probabilities.

### Step 1.4.4 — Return and Monte Carlo evaluation in a corridor

The classical example is a symmetric random walk over five cells:

```text
terminal           start             terminal, reward +1
   [0] ---- [1] ---- [2] ---- [3] ---- [4]
```

Action `0` moves left and action `1` moves right. The episode ends at 0 or 4; reaching 4 gives reward $+1$.

![A semi-cartoon corridor environment for the first RL example](assets/rl-for-llm/en/module-01/M1_corridor_world_EN.png)

The corridor is intentionally small, but it already contains the RL objects we need: the state is the current cell, the action is a left-or-right step, the reward is the event of reaching the right terminal, and a trajectory is the whole path before stopping. The point is not that this is a realistic environment; the point is that the formula can be checked before we transfer the same logic to tokens, responses, and LLM rollouts.

The behavior rule is fixed throughout this experiment: in every nonterminal cell, the agent chooses left or right with equal probability. We do not improve that rule after observing the episodes; we measure what it achieves. Rewards are undiscounted here, with $\gamma=1$.

The **state-value function** is expected return from a state:

$$
V^\pi(s)
=
\mathbb{E}_\pi[G_0\mid s_0=s].
$$

The starting cell is symmetric between the terminals, and the movement rule treats both directions equally. Without an artificial length limit, the walk reaches a terminal with probability one. Symmetry therefore assigns equal probability to each terminal, but only the right terminal pays a reward. The equiprobable policy starting in the center has

$$
V^\pi(2)=0.5.
$$

The code truncates an episode after 20 actions, so the exact value of the executed protocol is slightly smaller:

$$
V_{20}^{\pi}(2)
=
\Pr(\text{reach 4 by action 20})
=
\frac{1023}{2048}
=
0.49951171875.
$$

The fraction can be understood two moves at a time. Starting from the center, a pair of moves either reaches a terminal or returns to the center. The return-to-center probability is $1/2$. Remaining inside after twenty moves requires surviving ten such pairs, an event with probability $2^{-10}$. The remaining probability mass is split equally between the terminals, giving $\tfrac12(1-2^{-10})$ for reaching the right one—the fraction above.

This experiment measures **success within twenty actions**. The notation $V_{20}^{\pi}$ refers to that protocol; when it is treated as a finite-horizon task, the remaining budget also belongs in the state. It does not prescribe zero continuation value for every technically interrupted trajectory. If the original task allows further interaction, its evaluation must account separately for what lies beyond the collection boundary. Module 2 will develop that distinction.

The numerical difference is small, but the methodological point matters: compare an experiment with the task actually executed, not a nearly identical task with no horizon limit.

The **Monte Carlo method** estimates an expectation by an average over independent episodes:

$$
\widehat V_N
=
\frac1N\sum_{i=1}^{N}G_0^{(i)}.
$$

Here the return is Bernoulli with $p=1023/2048$, so the standard error at $N=1000$ is approximately

$$
\sqrt{\frac{p(1-p)}{1000}}\approx0.0158.
$$

Values such as 0.48, 0.50, and 0.52 do not contradict the theory; they reflect finite-sample noise. With $N=1000$, `seed=7`, and `max_steps=20`, the reference code returns `0.494`.

![Monte Carlo estimate convergence in the corridor](assets/rl-for-llm/en/module-01/M1_corridor_mc_EN.png)

The plot should not be read as a promise of neat monotone convergence: a finite estimate can sit above or below the exact value. The useful lesson is that the noise of an average over independent episodes shrinks on the order of $1/\sqrt{N}$, while the horizon and stopping rule must match the protocol actually implemented in code.

Collecting more independent episodes gives us a more precise estimate of this fixed policy. It does not make the agent increasingly likely to move right. **Evaluation reduces uncertainty about a behavior rule; learning must change the rule itself.** No action probability or model weight was updated from reward in this experiment.

The same logic will return in verifiable-reward training: several rollouts for one prompt provide a random quality estimate, and group size affects both variance and cost. Later modules will add policy improvement to the evaluation machinery.

### Step 1.4.5 — Takeaways and compact glossary

We can now return to the opening question: what must happen for a test result to change future decisions? We have separated the system that acts, the distribution behind its choices, and the evaluation of its consequences. We have also seen that changing temperature, measuring a fixed policy more accurately, and training from reward are three different operations.

The module's key conclusions are:

- An agent acts in an environment, receives rewards, and produces trajectories.
- A policy is a distribution over actions; under a token-level abstraction, an LLM exactly defines $\pi_\theta(a_t\mid s_t)$.
- A reward belongs to a transition; a return is an accumulated future outcome.
- In online RL, the policy changes the distribution of the next experience.
- A complete response can be modeled as a contextual bandit, token generation as an MDP, and a tool-using agent as a POMDP or semi-MDP.
- SFT, DPO, PPO-RLHF, GRPO/RLVR, and Best-of-N differ in data, feedback, updated components, and optimization location.
- The temperature result concerns pure softmax; a real decoding pipeline is broader.
- A more convenient reward or a larger rollout budget does not prove that the objective itself is correct.

Compact acronym glossary:

| Acronym | Full name | Role in the course |
|---|---|---|
| RL | reinforcement learning | policy learning from feedback and return |
| LLM | large language model | a model that can parameterize a policy |
| MDP | Markov decision process | a fully observed sequential model |
| POMDP | partially observable Markov decision process | a model with hidden state and observations |
| semi-MDP | semi-Markov decision process | a model in which actions have different durations |
| SFT | supervised fine-tuning | behavior cloning from demonstrations |
| RLHF | reinforcement learning from human feedback | an RL pipeline using human preferences |
| DPO | direct preference optimization | direct pairwise optimization from fixed preferences |
| PPO | proximal policy optimization | a near/on-policy policy-optimization algorithm |
| GRPO | group relative policy optimization | a PPO-like method with a group baseline and no learned critic |
| RLVR | reinforcement learning with verifiable rewards | RL with automatically checkable rewards |
| KL | Kullback–Leibler divergence | a measure of policy deviation from a reference |
| API | application programming interface | an external software interface to a model or tool |
